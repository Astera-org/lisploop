## First result

The complete GF(5) table for `y = a + 2*b` is generated by the simulator.
The learner receives its declared input/output frame, field vocabulary, and
bounds; the oracle program is kept outside learner inputs.

At 41 bytes, the enumerator completes the bound without finding a predictor.
After interruption and extension to 71 bytes, it finds `a + (b + b)`, along with
nine other valid expressions. Isolated decoding and replay succeed on all 25
inputs. Resumed and uninterrupted searches have identical candidates and work
totals. This is exhaustive validation over GF(5), not a claim about integers.

The search has two limits: the maximum encoded size of a candidate program and
the computation budget. **Interruption** means deliberately stopping when the
computation budget is reached, while keeping the search position and any unfinished
evaluation in memory; **resumption** continues that saved state with more work
available. **Extension** raises the program-size limit, here from 41 to 71 bytes,
so larger expressions become eligible. The experiment script chooses these limits
to check that pausing preserves progress and that larger solutions remain reachable.

| Representation | Description bytes | Execution work on 25 inputs |
|---|---:|---:|
| First verified formula | 71 | 2,000 |
| Packaged function lookup | 375 | 22,325 |
| Literal ordered output sequence | 65 | Different, whole-object task |

The formula does **not** compress the 65-byte output sequence under this
encoding. The lookup comparison includes an executable function of `(a,b)`;
the output-sequence comparison assumes an ordered whole-object target. Neither
comparison demonstrates a search speedup. Completing the 71-byte search costs
876,490 work units, including failures; its first solution arrives at 31,138.
Observation generation, baseline construction, and independent replay add
29,825 units to this experiment. Wall time and a separate supplied-decomposition
control appear in [milestone1.txt](intermediate_results/history-f6bf54ef/milestone1.txt).
Regenerate that record with `make m1`.

The objectives are declared before the experiment: pure description
`(lambda_run, lambda_search) = (0,0)` and positive work `(1/100,1/1000)`.
Results include `S`, `W_run`, `W_search`, `J = S + lambda_run*W_run`, and
procedure cost including acquisition. There is no residual in this exact
function-synthesis fixture. Observation generation is charged once; reorientation
charges processing without rerunning the experiment.

The only frame is `Frame(schema, rows)`; each row has `key`, `known`, and
`allowed`. Schema inputs are an alist of numeric variable IDs to types. Known
values follow that order. Keys are unique occurrence identities and never enter
the predictor environment. Equal-valued rows with different keys remain distinct.

Types are `:int`, `:bool`, `:index`, `(:gf p)`, `(:tuple ...)`, and `(:seq type)`.
Field literals must already be canonical residues. Field arithmetic results are
reduced modulo the declared prime; integer arithmetic is exact and has no fixed
bit-width limit. An integer and a field element remain different typed
objects even if their payloads are equal.

Expressions are `(:lit type value)`, `(:var id type)`, and
`(:app operator (arguments ...))`. An operator is a monomorphic
`(:op name type)` symbol whose signature is fixed by the simulator. Pattern
holes are `(:hole id type)`; an operator hole has a `(:fn inputs result)` type.
Models contain plain typed data and syntax, with no host functions or store
pointers. Treat trees, schemas, rows, and language records as immutable after
constructing a job; the implementation uses structural sharing.

**Encoding example: where do 11, 41, and 71 bytes come from?**

Description size is computed as `(length (canonical-string expression))`.
The encoding is ASCII, so every character, including parentheses and spaces,
occupies one byte. In this GF(5) experiment:

- Literal `2` encodes as `(0 (3 5) 2)`: **11 bytes**. The leading `0` marks
  a literal; `(3 5)` identifies the field type and its modulus.
- Variable `a`, with ID 0, encodes as `(1 0 (3 5))`: **11 bytes**.
- The typed addition operator encodes as `(3 0 (3 5))`: **11 bytes**.

The complete expression `a + b` encodes as:

`(2 (3 0 (3 5)) ((1 0 (3 5)) (1 1 (3 5))))`

The application tag, surrounding parentheses, and spaces add eight bytes to
the operator and its two operands. Thus the operator and application together
add 19 bytes beyond the operands:

$$
\begin{aligned}
S(a+b) &= 8+11+11+11 = 41,\\
S(a+(b+b)) &= 19+11+41 = 71.
\end{aligned}
$$

These sizes depend on the types and payloads: integer `2` encodes as `(0 0 2)`
and occupies seven bytes. Much of the current encoding is punctuation and
repeated type information; a more compact codec could change the thresholds
and compression comparison. Execution work is measured separately.

`finite-allowed` retains sets of **whole** values. A correlated tuple set is not
split into independent columns. `predicate-allowed` takes a checked Boolean AST
whose only free variable is the proposed value, ID 0. No Lisp callback is accepted.

`pullback-frame` builds a child requirement by passing a proposed child value
through a supplied parent decoder. For example, let the parent inputs be `(a,b)`,
the decoder be `y = a + z`, and the child's input binding select only `b`.
For the GF(5) observation `(a,b,y) = (1,2,0)`, the child receives `b = 2` and
proposes `z = g(2)`; a separate checker tests `(1 + z) mod 5 = 0`. The child
program cannot read `a`, `y`, the row key, or the checker. The synthesizer may
inspect the observations during discovery; this restriction concerns the
candidate program's runtime inputs. Bindings may select inputs or compute new
values from them, and are type-checked against the parent's declared inputs.

A **fiber** is the set of acceptable child values, here `{4}`. Pullback represents
it implicitly as a typed predicate in the child row's `allowed` field, without
listing its members. Tests independently enumerate tiny finite domains to check
that these predicates accept exactly the correct values. Synthesis does not
enumerate inverse fibers: this keeps pullback applicable to unbounded integers
and supports the later experiment of learning inverse rules. Ordinary explicit
finite sets remain supported: `finite-allowed` encodes their members as a typed
sequence literal inside a membership predicate. A fiber describes compatible
values; a **residual** is a particular value or index retained for reconstruction.

`compose-model` substitutes the child program and its input bindings into the
decoder. A child `g(b) = b+b` therefore produces the assembled program `a+(b+b)`.
The resulting AST includes and pays for all duplicated syntax; composition does
not require an explicit fiber table.

The runtime primitives are arithmetic `+`, `*`, equality, tuple construction,
membership, encoded lookup, and indexed gather. The last four support requirements
and supplied contract controls and are declared prior knowledge. **The default
search grammar enumerates only `+`, `*`, variables, and domain literals.** No
inverse, division, view sketch, AU pattern, or metadata shortcut is supplied to
the GF(5) discovery run.

Encoded lookup tables provide storage for residuals and incompressible data in
later models. The current `lookup-model` builder requires `:lookup-p t` in the
frame's schema, declaring that lookup models are admissible for the experiment,
and finite lists of concrete acceptable outputs, called **witnesses**. For repeated
inputs, one output must satisfy every corresponding row: if input `7` allows
`{1,2}` in one row and `{2,3}` in another, the table stores `7 -> 2`. Disjoint
allowed sets cause rejection. A predicate alone supplies a test but no explicit
witness list; the current builder does not solve it to obtain table entries.

The entries are stored as a typed literal inside the model, and their full
description size is charged. Lookup keys must come from declared runtime inputs
or computations on them. Occurrence-specific residuals therefore need an available
coordinate or an encoded selection/reassembly procedure; internal row keys do
not automatically become predictor inputs. Partitions retain an inverse
permutation; quotients retain an index for every occurrence. Their closed
`gather` programs reconstruct the full ordered object from encoded data,
including multiplicity.

## Search and interruption

```lisp
(load "load.lisp")
(in-package :lisploop)
(let* ((field (gf 5))
       (frame (orient-observations
               (list field field) '((0 0 0) (1 1 2) (2 2 4)) '(0) '(1)))
       (language (make-language field
                                (schema-inputs (frame-schema frame))))
       (job (start-search frame language)))
  (resume-search job 41 10)       ; cumulative work ceiling, not an increment
  (resume-search job 41 100000)   ; same continuation, larger ceiling
  (search-job-best job))
```

The enumerator advances through canonical byte sizes and retains every syntax
alternative in **buckets indexed by result type and encoded size**. These are
separate attributes: `(GF(5), 11 bytes)` contains `a`, `b`, and literals `0`
through `4`; `(GF(5), 41 bytes)` contains single-operation expressions such as
`a+b` and `a*b`. The size index selects operands that fit the requested program
length; the type index selects operands compatible with the operator's signature.
All expressions in this first arithmetic experiment have type GF(5), so the type
index becomes useful when a search language includes multiple result types.

Construction proceeds from smaller expressions already cached in completed
buckets. For example, a 71-byte application can combine an 11-byte operand and
a 41-byte operand, plus 19 bytes of operator/application overhead. Here a
"child" means an operand in the syntax tree; the earlier pullback discussion
uses "child" for a synthesis subproblem. Both operand orders are considered,
retaining alternatives such as `a+b` and `b+a`.

Available variables are listed explicitly in the frame schema's `inputs` field
and copied into the search language by `make-language`. The GF(5) fixture selects
columns 0 and 1 as inputs, giving variables `a` and `b`; column 2 is the target
`y`, available to the checker. Each row supplies values for those input variables.
The interface is finite because it lists finitely many variables, even when their
types, such as integers, admit infinitely many values.

This interface is fixed for a particular search job, but can change between
questions. `orient-observations` already supports different input/target selections:
recorded triples `c=a+b` can supply either `(a,b) -> c` or `(a,c) -> b`.
`pullback-frame` also supports computed child inputs, using values available to
the parent. Later rule and algebra experiments can choose suitable typed variables
for each question, and learned library calls will have declared parameter
signatures. Automatic interface selection and learned library calls remain future
work; the current interfaces are supplied explicitly.

Field literals are finite; integer literals are generated lazily by exact signed
decimal payload length. Together with the finite variable and operator vocabulary,
this ensures that every finite byte bound has finitely many candidates, including
over integers.

The search saves its enumeration position in an `enumerator` structure: the
current size and phase, position among variables or literals, current operator,
operand-size split, and indexes into the operand buckets. These **cursors** are
stored loop counters identifying the next combination to try. The surrounding
search job also retains the current candidate, remaining example rows, and any
unfinished evaluator state, so resumption continues without restarting that work.
Search charges enumeration, construction/indexing, row scheduling, and interpreter/
checker work according to the tariff below. Construction and evaluation charges
are now applied in batches, capped by the remaining work budget. An insufficient
budget leaves the unpaid portion in the saved state, so even a one-unit cutoff
remains exact. All work goes to the fixed enumeration and checking procedure;
there is no learned preference or equivalence-based pruning.

A **counterexample** is a supplied observation on which a complete candidate
fails its requirement. For `y = a + 2*b` over GF(5), the row `(a,b,y) = (0,1,2)`
rejects candidate `a+b`, which returns `1`. Search executes the candidate on each
row and checks its result against the allowed set or predicate, stopping at the
first failure. These counterexamples come from the supplied rows; the current
implementation counts the rejection without learning a generalized explanation.

A rejected candidate remains in its syntax bucket for use as a **subexpression**.
For example, `b` fails as a complete predictor but is essential inside `a+(b+b)`;
an operand need not produce the final target value. Successful candidates check
every row and remain available after a best solution has been found. They can be
ranked by description size plus a nonnegative weighted execution cost.

The VM retains its task stack, value stack, and any partially paid instruction.
Its statuses are `:unknown`, `:value`, and `:error`. A work cutoff leaves
`:unknown`; it is neither a semantic error nor evidence of impossibility.
Increasing the budget continues the same VM, including a suspended checker.

Messages have a call ID, claim, and evidence. A job retains its exact frame and
language; IDs associate candidates and outcomes with that job. `:bounded-exhaustion`
means all candidates through the reported bound have been checked, possibly with
successful candidates. `:cutoff` reports the last *completed* bound and current
phase. Neither is an unbounded refutation. The tiny independent reference checks
both the full syntax set and accepted set at a bound permitting at most one
application. The 71-byte experiment is not an independent optimality reference.

## Encoding and work tariff, version 1

The canonical form is an ASCII S-expression containing only decimal integers and
lists, with one space between elements and no trailing whitespace. `S` is its
byte length. `read-model` decodes it and checks types and input availability;
reader dispatch and reader evaluation are disabled. Encoding fixes the allocation:

| Item | Code |
|---|---|
| Literal, variable, application, operator, hole | Tags `0`, `1`, `2`, `3`, `4` |
| Integer, Boolean, index | Type IDs `0`, `1`, `2` |
| Field, tuple, sequence, function signature | Type tags `3`, `4`, `5`, `6` |
| `+`, `*`, `=`, tuple, membership, lookup, gather | Operator IDs `0` through `6` |

Every literal payload is included recursively. Booleans encode as `0`/`1`;
sequences and tuples encode their complete contents. The **codec** is simply the
encoder/decoder for this representation, including syntax holes. A hole with ID 0
expecting a GF(5) expression encodes as `(4 0 (3 5))`, occupying 11 bytes: `4`
marks a hole, `0` is its identifier, and `(3 5)` specifies its type. This lets the
system measure the description size of a pattern before its missing syntax is chosen.

**Instantiation** means substituting concrete syntax for those holes. For the
pattern `?h + ?h`, replacing `?h` with the literal `2` produces `2 + 2`;
replacing it with the declared variable `b` produces `b + b`. Both occurrences
of the same hole receive the same replacement. This is template substitution:
the expression itself is being completed. Lazy evaluation instead postpones
execution of an already specified expression. The current evaluator rejects
unfilled holes; a completed program may still read its declared runtime variables.
Pattern size measures only the template, so a complete reconstruction must also
account for its substitutions or the resulting instantiated program.

The work units are a published abstract tariff, not CPU instructions:

- Preflight costs the encoded AST bytes plus argument payload bytes, per call.
  It includes input/environment validation and syntax checking.
- Variable/application visits cost one; literals cost one plus payload bytes.
- Arithmetic over a fixed prime at most 257 costs one per primitive. Integer
  addition costs the larger operand bit length; multiplication costs their
  bit-length product, with a minimum bit length of one. Larger fields add a
  squared-modulus-bit-length reduction tariff.
- Equality, tuple, membership, lookup, and gather cost one plus input payload
  bytes. Search checks use the same VM and are charged to acquisition.
- Each enumeration cursor operation and scheduling transition costs one;
  syntax construction, validation, and indexing are charged by candidate bytes.
  Pullback/composition charge generated bytes; orientation and supplied views
  charge their data traversal. Matching/AU meter visited terms.

The evaluator calculates an instruction's tariff, then charges the smaller of
its unpaid cost and the available budget in one update. Once the instruction
is fully paid, its host operation executes atomically. A work cutoff preserves
any unpaid cost; it does not impose a wall-clock deadline on an individual host
operation. The tariff is an abstract cost measure, while wall time also includes
implementation overhead. Reporting/printing and test harness work are outside
the discovery ledger. `W_run` is a separate future deployment measurement;
replay during acquisition is charged to `W_search`.

## Scaling and batched accounting

The first implementation returned through the search loop for every tariff unit,
including each unit of a precomputed construction or instruction cost. The evaluator
already supported larger budgets, but search passed it only one unit at a time.
Search now batches those charges up to the remaining budget within each phase.
`resume-search` accepts an optional `:quantum` cap; `:quantum 1` retains one-unit
stepping for diagnostics. Candidate order, cutoff positions, and tariff version 1
are preserved. All 688 checks pass, including comparisons of the full saved states
and ledger categories between batched and one-unit execution.

The following measurements compare a frozen copy of the original kernel with
the batched implementation. Each run uses a fresh SBCL 2.6.4 process on the same
machine, a 2 GiB dynamic-space allowance, and all 25 GF(5) input pairs. The targets
are `a+2*b` at 71 bytes, `a+b*(b+2)` at 101 bytes, and `a+b*b*b*b` at 131 bytes.
Times are for **completing the entire bound**, rather than finding the first
solution. The two smaller cases report medians of three runs per implementation;
the largest reports one run per implementation. Loading, fixture generation, and
the final GC used to measure retained memory are excluded; GC during search is
included. Runs were serial and unprofiled.

| Bound (bytes) | Expressions retained | Before (s) | Batched (s) | Speedup |
|---:|---:|---:|---:|---:|
| 71 | 2,849 | 0.044 | 0.024 | 1.83x |
| 101 | 98,889 | 1.720 | 0.920 | 1.87x |
| 131 | 3,863,657 | 83.132 | 44.356 | 1.87x |

The largest run's CPU time falls from 83.09 to 44.33 seconds, closely tracking
elapsed time. Its additional live heap remains about 328 MiB and peak process
memory about 477 MiB, including the Lisp runtime. Cumulative allocation remains
about 67 GiB, mostly temporary objects; that is allocation traffic, not simultaneous
memory use. CPU time was the immediate bottleneck in these runs. Batching reduces
accounting overhead without reducing the number of retained expressions.
The discovery totals are unchanged: 876,490, 36,625,916, and 1,772,480,257 work
units, respectively. The earlier description and execution-cost results therefore
remain comparable under the same tariff.

A separate evaluator microbenchmark illustrates why batching matters most for
large instruction charges. For one multiplication of two 4096-bit integers, the
updated measurement is about **0.300 seconds with one-unit advances versus
0.092 milliseconds with batched advances**, roughly 3,300x faster. Both executions
produce the same result and charge exactly 16,782,182 work units. These are averages
of 3 and 1,000 executions, respectively. The earlier measurement of roughly
0.29 seconds versus 0.11 milliseconds was about 2,600x, not 2.6x. These ratios
describe this isolated evaluator operation; the complete searches above improve
by about 1.9x because enumeration, serialization, validation, and allocation still
consume time.

Wall-clock time is already an appropriate measure of practical search latency.
Report it alongside CPU time, peak/live memory, candidate counts, and the
deterministic tariff. The tariff supports reproducible budgets and interruption
checks; it is not a calibrated runtime predictor across implementations and
workloads. Use consistent hardware and repeated timings for short runs.
Repeated serialization and type/size computation remain candidates for future
optimization. Exhaustive retention also remains a scaling limit: the next
five-operation bound, 161 bytes, would contain about 162 million expressions
cumulatively in this grammar. That count is calculated, not a completed run.
The measured programs are still shallow; deep recursive synthesis remains untested.

### Deferred option: runtime compilation of DSL expressions

Revisit selective lowering of validated DSL expressions to compiled Lisp when
repeated execution warrants it. The evaluator itself is compiled, but DSL
expressions currently remain interpreted data. Likely first targets are frequently
reused frame predicates, accepted models, and later library functions; transient
search candidates may be discarded before compilation pays off. Frames would
remain structured data, with their executable expressions eligible for compilation.

Keep the typed AST, canonical encoding, and provenance as the authoritative
representation, with compiled functions cached by expression, input schema, and
relevant implementation versions. Preserve integer and finite-field semantics,
declared-input isolation, explicit errors, and exact tariff cutoffs. Compilation
would need budget checks and resumable state, or a fast path used only when the
budget is known to suffice, with VM fallback otherwise. Integer instruction costs
depend on intermediate values and cannot generally be prepaid as one fixed total.

First consider caching encoded sizes and validation results, then measure selective
compilation against that baseline. The break-even condition is
$C_{\rm compile} < N(T_{\rm interpreted}-T_{\rm compiled})$, where $N$ is the number
of subsequent executions and both execution times include required bookkeeping.
Include compilation time and retained code memory in the measurements; any abstract
compilation charge requires a declared tariff policy. This option is deferred,
with no DSL compiler implemented or speedup measured yet.

## Scope of the controls

`make test` covers the milestone 1 contract and the immediately recommended tiny
syntax controls: input isolation and reorientation, lookup replay with explicit
size and work costs, joint predicate/fiber agreement, empty fibers,
partition/quotient reconstruction, typed substitutions, operator holes, repeated
holes, matching, and aligned AU. Three of these controls mean:

- **Lookup replay with explicit costs:** the table is encoded inside the model,
  contributes to its description size, and consumes tariff units when executed.
  This is what "charged" means. Replay runs the encoded model again using only
  its contents and declared inputs; the test checks that it reproduces the outputs
  without access to the original observation table.
- **Joint predicate/fiber agreement:** the generated predicate must accept exactly
  the child values that satisfy the parent requirement. "Joint" preserves constraints
  on whole tuples: an allowed set `{(0,0), (1,1)}` must reject `(0,1)` and `(1,0)`,
  even though either coordinate alone may be `0` or `1`. Tests independently
  enumerate tiny finite domains and compare the acceptable values (the fiber)
  with the predicate's answers.
- **Empty fibers:** no child value satisfies the requirement through the chosen
  decoder. For example, `d(z) = (z,z)` cannot produce `(0,1)` or `(1,0)`.
  The test checks that the generated predicate rejects every possible `z` in
  the tiny domain. This establishes impossibility for that requirement and
  decoder, not for every possible decomposition.

The AU reference exhausts the finite flat patterns for all 64 pairs of single
GF(2) applications; it makes no unrestricted abstraction-optimality claim.
Other controls cover exact integer payload bounds, explicit errors, bit-sensitive
work, contradictory rows, shuffling, mid-check interruption, increasing limits,
and repeatable cost totals. Batched and one-unit execution are compared at
matching budget cutoffs, including partially paid construction and instructions,
candidate discovery, and errors. The comparisons include complete saved states,
syntax buckets, messages, candidate order, and every ledger category.

The supplied child trace uses the same search API and composes/rechecks its result.
Automatic view/decoder proposal scheduling, multi-level recursive orchestration,
backtracking, cross-call conflict routing, memory eviction, laws, inverse learning,
and library learning remain subsequent milestones. No binders, generated
recursion, e-graphs, general graph matching, or semantic pruning are implemented.
Checkpoints currently live in memory, and syntax retention grows with the bound.

## Milestone 2: observed equivalence and invariants

Milestone 2 adds a way to retain agreements discovered by execution. An expression's
**output vector** is the ordered list of its results on the declared input rows.
Expressions with the same result type and output vector share a **bucket**. Every
expression within the description bound remains in that bucket, so different
syntax remains available for later matching and abstraction. These are agreements
on particular observations; membership does not authorize rewriting other programs
or removing syntax from the canonical search.

The experiment records ten transitions under $T(a,b)=(a+1,b+4)$ over GF(5): five
successive steps starting at `(0,0)` and five starting at `(0,1)`. Each starting
state returns to itself after those five steps. Reorienting these records produces
20 input probes, one before and one after each transition. Their occurrence keys,
pair links, and the two selected starting rows remain outside predictor inputs.
The original transition frame is retained; making this view charges processing
work without executing the transition again.

The search enumerates expressions $h(a,b)$ using the existing field literals,
variables, addition, and multiplication. It seeks both $h(s)=h(T(s))$ on every
recorded pair and different values at the two starting states. Constant expressions
satisfy the first condition but fail the second. This is a search for an informative
observable; it does not yet reconstruct or compress the original observations.

### Result and controls

After an intentional cutoff at 100 work units and resumption with a 1,000,000-unit
ceiling, the search completes the 41-byte bound: **105 expressions form 25 output
buckets**. Exactly one bucket passes both
conditions, containing `a+b` and `b+a`. Both produce 0 throughout the first recorded
cycle and 1 throughout the second. All syntax alternatives, including constant
expressions and those that fail invariance, remain stored.

| Expression | Description bytes | Execution work on 20 probes | Observed result |
|---|---:|---:|---|
| `a+b` | 41 | 940 | Invariant and varies between starts |
| `b+a` | 41 | 940 | Same output vector; retained separately |
| Constant `0` | 11 | 300 | Invariant but uninformative |

Discovery costs **108,840 work units**, including enumeration, execution, scheduling,
and indexing. Original transition generation costs 1,270 and reorientation costs
60, for **110,170 units** through discovery. The two returned expressions then pass
six fresh transition pairs, starting at `(0,2)`, `(0,3)`, `(0,4)`, `(2,0)`, `(2,1)`,
and `(2,2)`; these source states were absent from discovery. Replaying both programs
costs 1,350 units, with another 798 for the fresh observations and their input view.
Changing the transition to `(a+1,b+3)` rejects both programs, recording the first
pair on which their values differ.

A separate control demonstrates why the scope matters. On inputs `{0,1}`, `x`
and `x*x` both produce `(0,1)` and share a bucket. Rechecking the retained expressions
on `{0,1,2}` gives `(0,1,2)` and `(0,1,4)`, respectively, so they occupy different
buckets in the new scope. All 78 expressions survive this recheck; the number of
buckets increases from 13 to 14. The original records still correctly describe
agreement on `{0,1}` and are left intact.

The evidence is **replayed observations**, including the fresh tests. There is no
full-domain law validation or symmetry-group inference here, and no compression
or search-speedup claim. The independent reference in the tests exhausts the tiny
single-application syntax bound and checks its output vectors; that establishes
the enumeration mechanism, not a universal semantic law.

### Integer-domain controls

The same observation machinery is tested over the unbounded integers (an infinite
ring, rather than a field). The transition is now $T(a,b)=(a+1,b-1)$, recorded for
three steps from each of `(-3,1)`, `(0,0)`, and `(2,3)`. These nine pairs give 18
probes containing negative, zero, and positive values. Search again discovers
`a+b` and `b+a`: their values stay at $-2$, $0$, and $5$, respectively, along the
three trajectories. Constant expressions fail the variation requirement.

This experiment explicitly declares the literal vocabulary `{-1,0,1}`, alongside
the two variables, `+`, and `*`. This restricts candidate syntax, **not integer
inputs or computed values**. It is a necessary practical distinction here: with
the default all-integer vocabulary and the existing text encoding, more than
$10^{22}$ literal expressions are shorter than the 29-byte integer `a+b`.
Each byte bound is finite, but exhausting that default grammar is impractical.
The default remains available; this control makes no discovery claim for it.
Within the declared vocabulary, a 31-byte bound covers five leaves and all fifty
ordered single applications, including the extra byte for each negative literal.
An independent arithmetic reference checks this complete set and its output vectors.

The 55 expressions form 19 buckets, with one informative invariant bucket retaining
both sums. Each sum costs **29 description bytes and 659 execution units** over
the 18 probes. Discovery costs **41,204 work units**, plus 896 for original
transition generation and 54 for reorientation. These costs use the existing
encoding and tariffs; they are not a speed comparison with the GF(5) experiment.

Fresh replay uses six starts with $N=2^{256}$:
$(N,-N)$, $(N+1,-N)$, $(-N,N)$, $(-N-1,N)$, $(N,N)$, and $(-N,-N)$.
Both programs preserve the exact sums $0,1,0,-1,2N,-2N$ across their transitions.
This checks cancellation, signs, large outputs, and the distinction between
adjacent large integers. Replay costs 13,384 units, with 5,550 for fresh acquisition
and orientation. Changing the transition to $(a+1,b-2)$ rejects both invariants.

The integer `x` versus `x*x` control likewise splits its original agreement on
`{0,1}` when tested on `{0,1,-1,2,N,N+1}`; all 36 expressions remain stored.
Exact squares are checked against host integer arithmetic. Unit-step and batched
jobs agree at successive work cutoffs even during large multiplications, checking
that larger values incur their bit-sensitive work and resume correctly.
All these results remain **finite, scoped observations**. They test the machinery
needed downstream without establishing laws over all integers or learning inverses.

### Scaffold and use

`observations.lisp` adds an observation scope, per-expression execution records,
and an index of buckets over an ordinary frame. The scope retains a snapshot of
the input rows, domain, literal vocabulary and language version, simulator version, typed-value equality,
and any pair/start selections. Row requirements are not consulted by this index;
each candidate receives only the declared input values. Neither duplicate input
values nor shuffled storage removes occurrence identity.

`make-observation-scope` establishes that context, and `start-observation-search`
uses the existing enumerator and VM. `resume-observation-search` accepts a growing
description bound and a cumulative work ceiling. It preserves unfinished setup,
construction, evaluation, and indexing work. `find-observation` retrieves a program's
record; `observation-invariants` returns the informative buckets. Supplying
`:expressions` starts a replay job for an explicit list, useful when testing retained
syntax on a new scope. Its `:replay-complete` message covers only that list; it
does not claim to have exhausted the grammar.

`make-language` accepts `:literals :all` (the default) or an explicit list of
domain values, such as `:literals '(-1 0 1)` for the integer controls. Duplicate
literals are removed, and each remaining literal is enumerated at its actual
encoded size. The scope copies this vocabulary along with the rest of the grammar.

Complete output vectors enter buckets only after all probes finish. Errors retain
their work, failing row, and diagnostic but supply no equality evidence. Interrupted
evaluations remain unknown. `observed-agreement-p` requires complete records with
matching types in the exact same scope; matching scope labels alone are insufficient.
The records are treated as immutable after construction.

The evaluator and description tariffs remain unchanged. Observation jobs additionally
charge setup by the input payload and selection counts, and indexing by the output
payload size plus pair/start comparison counts. These are deterministic abstract
tariffs; wall time is reported separately. Rechecking a larger frame currently
executes the retained programs on all its rows again, including the earlier inputs.
It reuses the recorded transition data, but does not yet cache execution prefixes.

`make test` includes the new discovery, fresh-data, changed-transition, accidental
agreement, type/scope isolation, occurrence, error, and interruption controls.
Single-unit and batched execution must preserve the complete saved state and every
work category at matching cutoffs, including large integer instruction costs.
Before the bit-codec extension, the combined suite passed **25 tests and 1,081 checks**.

Run `make m2` for the complete trace and per-stage work ledgers in
[milestone2.txt](intermediate_results/history-f6bf54ef/milestone2.txt). The evidence records and retained
syntax are the interface for later law proposals; the original frames remain
available for later prediction orientations. **Milestones 3 and 4 are not implemented
or run:** there is no learned-law application, inverse-rule search, inverse-value
enumeration, or semantic pruning.

## Bit-cost experiment: encoding v2

The v1 integer control exposed a description-cost problem: punctuation and repeated
type annotations made `a+b` cost 29 bytes, while more than $10^{22}$ integer
literals were shorter. Merely converting byte counts to bits leaves that ordering
unchanged. Encoding v2 replaces the text representation used for description cost
with a compact, decodable binary representation. Text serialization remains useful
for inspection, and the default `:bytes-v1` experiments above retain their meaning.

`bit-codec.lisp` supplies an actual encoder and decoder, not just a weighting formula.
`bit-description-size` counts the bits emitted by that encoder. A standalone packet
contains the encoding version, ordered input IDs and types, result type, profile
selector, and expression body. The header is charged **once per model**; nested
expressions do not repeat it. Both total and body sizes are reported below. Input
IDs and types declare the argument interface; replay supplies only the declared
row values.

### Coding choices and scope

The arithmetic profile uses the following prefix tags. Operator arity and operand
types follow from the declared arithmetic domain, so no parentheses or repeated
internal type annotations are needed.

| Tag | Node | Additional bits |
|---|---|---|
| `00` | Variable | Slot in the ordered input schema |
| `01` | Literal | Typed value payload |
| `10` | Addition | Two expression bodies |
| `11` | Multiplication | Two expression bodies |

A variable slot costs $\lceil\log_2 m\rceil$ bits for $m$ declared inputs (zero
bits when there is only one). A GF($p$) literal costs $\lceil\log_2 p\rceil$
payload bits; unused bit patterns are rejected. Integer $n$ maps to a positive
integer $z=2n+1$ for $n\geq0$, or $z=-2n$ for $n<0$. With
$L=\lfloor\log_2 z\rfloor+1$, its self-delimiting payload costs

$$D(z)=L+2\lfloor\log_2 L\rfloor.$$

Concretely, encode the bit length $L$ as its binary representation preceded by
one fewer zero than its own bit length; then append the lower $L-1$ bits of $z$.
The decoder can recover each boundary without separators. Including the literal
tag, `0` costs 3 bits, `-1` and `1` cost 6, and `-3,-2,2,3` cost 7. Integer
`a+b` has an 8-bit body, so exactly seven integer literals are strictly shorter.
An integer of magnitude $2^{256}$ has a 276-bit literal body; there is no maximum
integer value or restricted vocabulary in the v2 runs.

The header uses the same positive-integer code for version `2`, input count plus
one, and each input ID plus one. Three-bit type tags identify integers, Booleans,
indices, fields, tuples, and sequences; field moduli and tuple arities are encoded
explicitly. The profile selector costs one bit. The two-input integer header costs
23 bits; the GF(5) header costs 38 bits. A general profile supports the rest of
the current executable DSL, including lookup tables, tuples, sequences, predicates,
and reconstruction. It uses three-bit node tags, with a fourth bit distinguishing
lookup from gather, and encodes operand types when the result type does not
determine them. Sequence lengths and index values use the positive-integer code
after adding one; tuple values concatenate their typed components. The decoder
rejects truncated packets, trailing bits, and noncanonical profile choices.

The profiles and code allocation are supplied prior knowledge. Search v2 currently
covers the homogeneous arithmetic grammar; the richer profile encodes explicit
baselines and replay models. No learned coding distribution or free library has
been introduced.

For this experiment, **execution and acquisition tariffs stay at v1**. In particular,
construction and validation still charge the text-size tariff, while integer
arithmetic still charges operand bit lengths. Only description scores and enumeration
order use v2 bits. Thus the same program on the same inputs has the same execution
work under both descriptions. Search messages identify the selected cost model.

### Milestone results

| Run | Completed bound, bits | Retained expressions | Result size: header + body | Discovery work |
|---|---:|---:|---:|---:|
| M1 GF(5), `y=a+2b` | 53 | 649 | `a+(b+b)`: $38+13=51$ | 250,320 |
| M1 integers, `y=a+2b` | 36 | 435 | `a+(b+b)`: $23+13=36$ | 79,411 |
| M2 GF(5), invariant | 46 | 15 | `a+b`, `b+a`: $38+8=46$ | 16,870 |
| M2 integers, invariant | 31 | 27 | `a+b`, `b+a`: $23+8=31$ | 18,990 |

The GF(5) M1 run first completes 46 bits without a predictor, then extends to
53 bits, the encoded size of the supplied data-generating oracle `a+2*b`.
It retains ten valid formulas and first accepts `a+(b+b)` at 33,250 work units.
Its execution work remains 2,000 over the complete 25-row domain. Original
acquisition, lookup construction, and independent replay add 29,825 work units.
The contradictory-output control still finds no predictor.

The same codec gives the executable lookup baseline **313 bits** and the literal
25-output sequence **104 bits**, versus 51 for the formula. This changes the
description-size ordering relative to v1's 71-byte formula and 65-byte sequence.
The function and ordered sequence still represent different tasks: a complete
sequence-compression claim must account for its input grid and ordering too.
Lookup execution remains 22,325 work units, and both models decode and replay
successfully. The v2 objectives use weights $(0,0)$ and $(1/100,1/1000)$ with
description measured in bits; these are newly declared objectives, not numerically
equivalent conversions of the byte-based objectives.

The integer M1 control uses all 25 inputs in $[-2,2]^2$. It retains six valid
formulas and first accepts `a+(b+b)` at 28,812 work units. The returned formula
passes six fresh signed input pairs around $2^{256}$, with execution work 1,562
on training rows and 4,368 on fresh rows. Both datasets are generated through
the metered simulator. This is finite observational validation over integers.

M2 uses the same transitions and observations as the earlier experiments. Exactly
one informative bucket retains both `a+b` and `b+a`; constants still fail the
variation requirement. Both expressions pass six fresh transition pairs and fail
when the transition changes. The integer fresh inputs include cancellation and
adjacent values around $2^{256}$. The `x` versus `x*x` controls split agreement
when new inputs are added, retaining all syntax and the original scoped evidence.
The larger-value execution costs and fresh-data work remain as reported for v1.

There is an important comparison at a matched syntax set: extending GF(5) M2 to
**50 total bits (12 body bits)** includes exactly the same 105 expressions as
v1's 41-byte bound. This costs **114,512** work units, versus **108,840** for v1.
The current size-indexed enumerator spends more cursor steps scanning empty sizes
and operand splits. The lower work at the 46-bit bound therefore reflects a smaller
candidate set, not a general implementation speedup. Likewise the two M1 bounds
include different syntax sets: v2 does not simply rescale the old search.

### What this establishes, and what remains adjustable

The change removes the immediate integer-literal bottleneck without restricting
the domain or vocabulary, and preserves interruption, extension, replay, and
scope boundaries. The tests compare enumeration against independent trees built
by application count, verify output vectors against host arithmetic, test signed
payload boundaries and malformed packets, and compare complete saved states under
unit-step and batched execution. The combined suite passes **31 tests and 8,697
checks**. No milestone 3 or 4 work is performed.

Further amendments should retain a decoder and an explicit accounting boundary.
In particular, shared schema costs could be amortized once per declared batch;
the integer code and the special arithmetic profile express prior preferences
that could be compared with other published codes; and enumeration can avoid
scanning impossible sizes without changing the objective. If we change work
tariffs to match binary processing too, that should be a separate version and
experiment. Finite bit bounds still have exponentially many possible payloads;
this pilot fixes the severe small-expression distortion, not general search growth.
