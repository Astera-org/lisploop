# Common brief for the round-3 reproductions

## What this is

`/home/tlh24/lisploop` holds a program-induction kernel in Common Lisp and a planning document,
`plan_v2c.md`, for rewriting it around one store: spaces (sets of rows), columns, hash-consed terms, and
classes (terms with the same column on a space). An outside reviewer wrote `plan_v2c_audit.md`. Its
section 2.5 and Appendix B make new claims about how heuristics, vocabulary, residuals and memory fit
together. The owner wants those claims **verified independently before they go into the plan**. Earlier
plans were rejected for unverified imports, so a claim that only "looks right" is not good enough, and a
clear "this does not reproduce" or "this was true only by construction" is as valuable as a confirmation.

Vocabulary used below:
- a **quotient** (a "word") is a small term that maps a value to one of a few labels: `sgn x`, `x mod 2`,
  `min(len xs, 5)`;
- a **verb table** is, for one operator and one quotient, the table from the labels of the inputs to the
  set of output labels seen (with counts), got by one group-by over probe evaluations of the operator;
- the **dependency score** ("lumpability" in the review) of a quotient q for an operator f is
  `1 - H(q(f(x)) | q(x)) / H(q(f(x)))`;
- **plain search** is bottom-up enumeration by size with behaviour dedupe (one representative per
  distinct column of values on the task rows).

## How to verify

For each claim in your task:
- First run the reviewer's script and record whether it prints the number the review reports.
- Then read the script and say plainly **what was computed and what was merely asserted or built in**:
  a hard-coded list labelled as the output of a selection rule, a "result" that follows from how the
  experiment was set up, a hand-written pool described as enumerated, probes hand-matched to the
  quotients being tested, an answer size handed to the search.
- Then test the claim with your own independent implementation (reusing the verify-quotients code is
  fine; reusing the reviewer's code is not), in the form the claim would have to take inside the kernel:
  nothing listed by hand that the kernel would have to find for itself.
- Vary the things the reviewer fixed (seed, probe count, task set, grid) enough to know whether the
  result is stable.

## Report format

Write your report to the path given in your task and also return it as your final message. Keep it under
about 1,200 words plus tables. Structure:

1. **Bottom line**: two or three sentences.
2. **Verdict table**: one row per claim: the claim as the review states it; REPRODUCED / PARTLY /
   NOT REPRODUCED / TRUE BY CONSTRUCTION / COULD NOT TEST; the number you got next to the review's.
3. **What changes for the plan**: the few findings a designer must not miss, each with its number.
4. **Supplied by hand**: everything in your experiment, and in the reviewer's, that a kernel would
   have to discover for itself and did not.
5. **Commands**: script, log, runtime for every table.
6. **Not done / could not check**.

Plain words; define any term you introduce; no claim without a number or a line reference.
